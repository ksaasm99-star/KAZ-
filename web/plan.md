# خطة Web App لمشروع KAZ

## قرار النطاق

هذا العمل يخص Web App الرسمي داخل `/home/ubuntu/kaz-work/web` في نفس مستودع KAZ. تطبيق Android الموجود في جذر المستودع يبقى دون حذف أو إعادة كتابة. الواجهة الويب هي قناة تشغيل وإدارة هاتفية لمصنع KAZ، وليست مشروعًا منفصلًا ولا نسخة تجريبية منفصلة. لا نعتمد في هذه الدورة على كمبيوتر المستخدم أو واجهة سطح مكتب.

الهدف هو بناء واجهة عربية RTL، Mobile-first، تتيح للمستخدم إنشاء مشروع، وصف فكرة التطبيق، متابعة التحليل والبناء، مراجعة الملفات والنتائج، محادثة KAZ داخل سياق المشروع، إدارة النماذج، ورؤية حالات الفشل والأدلة بصدق.

## التقنية المعتمدة

- **Frontend:** React 19 + TypeScript + Vite، مع مكونات React صغيرة قابلة لإعادة الاستخدام.
- **Styling:** نظام CSS tokens وCSS responsive الموجود في KAZ؛ لا تُضاف مكتبة تصميم جديدة لمجرد الزخرفة، لأن النظام الحالي يدعم RTL والجوال بالفعل.
- **Backend:** مسارات API داخل Vite middleware الحالية، مع عقود JSON typed في `src/memoryApi.ts`.
- **Persistence:** SQLite عبر `server/persistentMemory.ts`، وهو مصدر الحقيقة للمشاريع والأرشيف والهوية والنماذج والأدلة.
- **AI:** مسارات Gemini الحالية تكون fail-closed عندما تكون `KAZ_API_ENABLED` أو المفاتيح غير متاحة، مع بقاء Ollama عبر `ollamaGateway.ts` وNetworkBroker وفق الموافقة.
- **Android path:** تُحافظ الويب على عقود API والأنواع المستقلة عن الواجهة. لاحقًا يمكن تغليف الويب عبر Capacitor، أو إعادة بناء واجهة native فوق نفس العقود؛ لا يتم خلط Compose مع React داخل نفس الشاشة. هذا المسار مؤجل ولا يدخل في إغلاق Web الحالي.

## تصميم التجربة

البدائل المختصرة:

1. لوحة عمليات داكنة عربية مستوحاة من observability الحديثة — احتمال 0.76.
2. مساحة عمل فاتحة شبيهة بمدير ملفات — احتمال 0.08.
3. واجهة تسويقية زجاجية واسعة — احتمال 0.06.

تم اختيار البديل الأول.

- **Design Movement:** لوحة تشغيل عربية هادئة تجمع بين command center ودفتر أدلة.
- **Core Principles:** الحالة قبل الزينة، مصدر الحقيقة ظاهر، الفشل صريح، ومسار العمل قابل للتراجع.
- **Color Philosophy:** الخلفية الكحلية تقلل الضوضاء، السماوي يرمز للفعل المسموح، الأخضر للتحقق، البنفسجي للأرشيف/المعرفة، والبرتقالي أو الأحمر للتحذير والفشل.
- **Layout Paradigm:** شريط سفلي ثابت ومناطق لمس واضحة على الجوال، مع مساحات عمل متدرجة بدل لوحة سطح مكتب مزدحمة. أي دعم لشاشات أكبر يكون تكيفيًا فقط وليس هدفًا مستقلًا.
- **Signature Elements:** علامة KAZ المدارية، شرائح حالة صغيرة، وأرقام/بصمات تقنية بخط واضح.
- **Interaction Philosophy:** كل زر فعل حقيقي أو حالة معطلة مفسّرة؛ لا يوجد زر يوحي بتنزيل أو بناء لم يحدث.
- **Animation:** انتقالات قصيرة للحالات والبطاقات فقط، بدون حركة تخفي الانتقال أو تغيّر المصدر الحقيقي.
- **Typography:** Tajawal للنص العربي، وSpace Grotesk أو monospace للقيم التقنية والمعرفات.
- **Brand Essence:** مصنع عربي صريح يحول الفكرة إلى مسار بناء قابل للمراجعة؛ دقيق، هادئ، ومسؤول.
- **Brand Voice:** مباشر ومحترم؛ أمثلة: «لم يبدأ التنفيذ بعد» و«تم التحقق من البصمة الفعلية».
- **Wordmark & Logo:** علامة مدار/نواة KAZ الموجودة في الواجهة، مع عدم استبدالها بنص عادي.
- **Signature Brand Color:** السماوي `#7de7e4` على خلفية `#07111f`.

## بنية الواجهة

- `src/App.tsx`: حالة التنقل، تحميل المشاريع، الأرشيف، والإشعارات.
- `src/screens/HomeScreen.tsx`: الصفحة التعريفية الأولى ومسار الدخول إلى مساحة العمل.
- `src/screens/BuildScreen.tsx`: إنشاء مشروع وكتابة الوصف واختيار محرك البناء.
- `src/screens/ProjectWorkspaceScreen.tsx`: نظرة عامة، المصادر، معرفة المشروع، المحادثة، معاينة المصنع، Diff والموافقة.
- `src/screens/ModelManagementScreen.tsx`: Model Registry وOllama عبر API حقيقي وحالات BLOCKED.
- `src/screens/ConversationScreen.tsx`: المحادثة العامة المنفصلة عن هوية المشروع.
- `src/screens/SettingsScreen.tsx`: هوية KAZ والإعدادات العامة.
- `src/memoryApi.ts`: عقود طلبات API فقط، دون منطق تخزين داخل المكونات.
- `server/*.ts`: الخدمات الأمنية والذاكرة والتحليل والمصنع؛ الكتابة الحساسة تبقى خلف Policy/Approval/Executor.
- `public/manus-routes.json`: مصدر المسارات المعلن للمنصة، ويظل متزامنًا مع صفحات الويب.

## قواعد التشغيل والأمان

1. لا تعديل على Android من مهمة واجهة الويب.
2. لا أسرار في React أو Git؛ Gemini وGitHub وOllama تُستدعى من الخادم فقط.
3. `KAZ_API_ENABLED=false` أو غياب المفتاح يعني BLOCKED/503، وليس نجاحًا وهميًا.
4. أفعال الكتابة أو البناء تعرض حالتها الحقيقية وتبقى مرتبطة بالمشروع والسجل والأدلة.
5. البيانات غير الموثوقة من الملفات أو الويب تبقى بيانات؛ لا تغيّر سياسة النظام.
6. دعم النص والصوت يمر عبر نفس عقد الرسالة، مع تحديد `inputMode` بوضوح.
7. كل شاشة تعمل RTL وتُختبر على عرض جوال حقيقي أو محاكي؛ لا نضيف متطلبات أو وظائف خاصة بسطح المكتب في هذه الدورة.

## التنفيذ المرحلي

1. تثبيت أساس الهوية والتنقل والـ route manifest.
2. تثبيت تدفق Home → Dashboard → New Project → Project Workspace.
3. ربط الحالات الحقيقية للمشروع والذاكرة والأرشيف.
4. ربط محادثة المشروع والصوت وحارس الهوية، مع عرض الأدلة والأخطاء.
5. ربط تدفق المصنع والمعاينة المباشرة لـ compile/build/APK دون ادعاء.
6. ربط Model Registry وOllama مع Q4_K_M وBLOCKED عند غياب المحرك.
7. مراجعة الجوال وRTL، ثم فحص TypeScript وbuild واختبارات المسارات القائمة من بيئة الويب؛ لا يتطلب الإغلاق جهاز كمبيوتر لدى المالك.

## قرار الإيقاف

لا يتم بدء مرحلة Android packaging أو إضافة خدمة خارجية جديدة قبل إغلاق أساس الويب واختبار المسارات الحقيقية، ولا يتم اعتبار زر واجهة منجزًا إذا كان لا يستدعي API أو لا يوضح سبب التعطيل. ميزات سطح المكتب أو التشغيل المحلي على كمبيوتر المستخدم خارج نطاق هذه الدورة.


## P3 — App Factory Execution Pipeline

### قرار المرحلة الأولى
نبدأ بتقوية عقد Typed Factory Request وإضافة سجل أنواع مشاريع قابل للتوسعة عبر configuration/registry، ثم نربطه بخطة الملفات قبل لمس التنفيذ الفعلي. الأنواع الأساسية الحالية هي Android وWeb وCLI وHybrid، مع إبقاء مولد Android الحالي متوافقًا. إضافة نوع جديد لاحقًا تكون عبر تعريف registry/config ومولد مستقل، لا عبر نسخ pipeline أو تعديل منطق الموافقة والتنفيذ.

### حدود هذه الدفعة
- لا كتابة ملفات مشروع قبل Approval صالح.
- لا تعديل Android الأصلي في جذر KAZ.
- لا إضافة نظام مشاريع أو Evidence Ledger أو Approval جديد.
- لا بناء APK في هذه الدفعة؛ نثبت فقط Typed Request وProject Type Registry وFile Plan contract.
- كل طلب يحمل `traceId/requestId` و`inputDigest`، وكل نتيجة غير مثبتة تبقى PARTIAL أو BLOCKED.

### البنية
- `src/agent/factoryProjectTypes.ts`: تعريف الأنواع وتوسعة registry من config آمن.
- `src/agent/factoryRequest.ts`: العقد typed والبصمة والتحقق.
- `server/multiFileGenerator.ts`: مولد Android الحالي، مع عقد platform-neutral لاحقًا.
- `server/executionPipeline.ts`: Planner → Policy → Approval → Executor الموجود، ولا يُعاد بناؤه.
- `server/persistentMemory.ts`: مصدر Evidence Ledger وSQLite الموجود.

### معيار إغلاق الدفعة
Typed Request يقبل الحقول المطلوبة ويكشف التلاعب، registry يحمّل تعريف نوع إضافي من config في اختبار حقيقي دون تعديل pipeline، وFile Plan يرفض target غير مسجل أو خطة غير آمنة. بعدها تتوقف الدفعة لمراجعة المالك قبل Snapshot/Atomic Apply أو Build.
